# Update main PR pipelines from release branch push pipelines

The [Update main PR pipelines from release branch push pipelines workflow](../.github/workflows/update-main-pr-pipelines.yml)
runs only when manually dispatched. It updates `main`'s PR pipelines using
push pipelines from the configured release branch (currently `rhoai-3.7-ea.1`) as a
reference, applying `tekton-templates/main-pr`. It then opens a PR using `gh pr create`
from a fresh branch named
`automation/update-main-pr-pipelines-<run-id>-<attempt>`.
It never pushes directly to `main`. If no files change, no PR is created.

The source release branch is set explicitly by `parent_ref` in
[`tekton-templates/main-pr/config.yaml`](../tekton-templates/main-pr/config.yaml), not detected
automatically. Update that setting when the latest release branch changes.
The shared `validate-tekton` tool performs the template-based updates; this is
not a direct file copy of the release push pipelines.

Before updating existing files, `script/generate_main_pr_children.py` reuses
`lib.tekton_children.plan_children` and the seed/safety policy from
`tekton-templates/release-pr` to create missing children. It reads parents from
Git into an in-memory staging map, retaining component-directory boundaries,
and applies the **main PR template**, not the release PR template. Existing
children (including aliases) are not regenerated; the normal validator updates
them afterward. Main-only PRs without release parents are preserved and reported.
Ambiguous parents/children and filename/name collisions fail before new files
are written. Parent files are never copied into main.

New filenames use the parent's unversioned component identity, which may be a
shortened name such as `odh-wb-…`. New PipelineRun names reserve space for a
ten-digit PR number. Exact component-label matching keeps these shortened names
associated with their parents on subsequent runs.

## Repository exclusions and release-derived children

[`tekton-templates/main-pr/generation.yaml`](../tekton-templates/main-pr/generation.yaml)
controls **creation of missing PR children on main only**. Its
`excluded_repositories` mapping uses exact `pipelineruns/<repository>` directory
names and requires a nonempty reason for each exclusion. Initially,
`RHOAI-Build-Config` and `rhods-operator` are excluded. To add another repository,
add its exact directory name and reason; globs and paths are rejected. An empty
mapping explicitly permits creation for every repository. A missing or malformed
policy fails before any child is created.

Excluded repositories' release parents are omitted from creation planning, and
a final check rejects any new child targeting an excluded repository. The log
reports each exclusion and reason. Existing PR files are not deleted or
regenerated by this step (the normal validator can still update them); push
files and release-branch generation are unaffected.

For eligible repositories, each release push parent should have a corresponding
main PR child. For example, both `odh-db-operator-v3-7-ea-1-push.yaml` and
`odh-db-operator-e2e-v3-7-ea-1-push.yaml` produce PR counterparts under
`pipelineruns/rhai-db-operator/.tekton/`. They intentionally inherit the release
component, service account, and build settings, with main-specific PR trigger
and pipeline revision transformations. An additional main-only E2E push pipeline
is left untouched; it neither suppresses creation nor supplies the PR's settings.

## PR cluster routing

KC main PR routing is owned by `all-pipelineruns/pull-request.yaml.j2`, not by
`main-pr` generation templates. After generation-specific fix and validation,
`script/conform_main_pr_children.py` applies central PR conformance and checks it
again before publication. It plans and validates every PR change before writing,
rejects ineligible or malformed inputs, and never modifies push files.

The central template declares `konflux_cluster == "stone-prod-p02"` around the
entire expression, including both notebook sync and ordinary path arms. It also
excludes the qualified and bare Power/Z platform values from existing arrays,
retaining empty arrays and missing parameters without file/parameter deletion.

`release-pr` remains unchanged: its outputs live in component repositories and
retain their own explicit destination guard. The main notebook generator still
strips inherited cluster predicates before constructing its OR expression, so
central conformance can safely apply one outer guard.

Validation compares the desired child CEL against the current annotation;
autofix writes that desired state. A valid push parent is not itself reported
as drift merely because the child's selectors differ.

This depends on shared tooling containing `ensure_cel_selectors` and
`ensure_cel_tekton_filename`. Parent routing
must be a standalone string equality (not `has(konflux_cluster)` or an OR-based
routing expression); unsupported forms produce validation errors. The rollout
assumes every P02 Repository CR already provides an unfiltered
`konflux_cluster: stone-prod-p02` parameter. A genuinely absent parameter causes
a PaC CEL checking error, not a null comparison or fallback.

## Notebooks PR trigger policy

The default template uses
`ensure_cel_selectors({'event': 'pull_request', 'target_branch': ABSENT})`
followed by `ensure_cel_tekton_filename(filename)` to retain unrelated release
push guards and paths under explicit pull-request checks. The central PR
conformance template applies the destination-cluster guard afterward.
The directory-mapped overlay `tekton-templates/main-pr/notebooks/pull-request.yaml.j2`
adds a separate build arm for PRs from `main` to `stable` that change
`manifests/rhoai/base/params-latest.env`.

The overlay also corrects the inherited params-file veto with
`files.all.exists(p, p != "manifests/rhoai/base/params-latest.env")`.
Consequently, mixed source-and-params changes build, ordinary params-only PRs
skip, and params-only main-to-stable PRs build. An unrelated main-to-stable PR
does not automatically bypass image path conditions.

Repository overlays fall back after component-label and component-prefix
overlays. Both creation and revalidation select the same directory-mapped overlay.
This requires shared tooling with repository-overlay and selector-stripping
support; the workflow's existing validator ref must contain that support before
using these templates. No workflow ref is changed by this template update.
Release-branch push triggers remain unchanged.

## Running it

In GitHub Actions, select **Update main PR pipelines from release branch push pipelines**, choose the workflow
branch, and click **Run workflow**. The selected ref supplies `tekton-templates/main-pr`;
the PR pipelines being updated always come from `main`, and `parent_ref` in the
selected config determines the source release branch.

The workflow must first exist on the repository's default branch for GitHub
to expose manual dispatch. The templates must also be committed to the selected
workflow ref.

## Retriggering individual component builds

The PR template enforces an exact, component-specific comment command:

```yaml
pipelinesascode.tekton.dev/on-comment: "^/build-konflux (odh-model-controller|all)$"
```

The command uses the `appstudio.openshift.io/component` label inherited from
the release pipeline, with its version suffix removed (for example,
`odh-model-controller-v3-7-ea-1` becomes `odh-model-controller`). The PR filename
does not determine the command. For example:

- `/build-konflux odh-model-controller` retriggers only the controller pipeline.
- `/build-konflux odh-model-serving-api` retriggers only the serving API pipeline.
- `/build-konflux all` retriggers every pipeline using this template in the repository.

The start and end anchors prevent a component command from matching sibling
pipelines. The template replaces existing comment patterns, including broad or
custom patterns. Bare `/build-konflux` no longer retriggers these pipelines.
To retrigger all components in a repository, post `/build-konflux all` as a
single comment. The annotation uses regular-expression alternation to accept
either the exact component name or `all`; it is one regex, not a comma-separated
list of patterns or duplicate annotation keys.

This takes effect in downstream repositories after running this automation,
merging its generated PR, and syncing the updated PipelineRuns to those repos.
Changing the template alone does not update existing downstream PipelineRuns.

## Dependencies and behavior

- Checks out `red-hat-data-services/devops-shared-resources` at `validate-tekton-dev`, which
  must contain `scripts/validate-tekton` and its supporting `lib` modules.
- Uses `uv run` to install the validator's inline Python dependencies.
- Fetches the target repository's full history so the templates can read
  parent push pipelines from the configured `parent_ref`.
- Runs the equivalent of:

  ```sh
  uv run ../source/script/generate_main_pr_children.py \
    --path . --tooling ../validator \
    --config-dir ../source/tekton-templates/main-pr

  uv run ../validator/scripts/validate-tekton \
    --config-dir ../source/tekton-templates/main-pr \
    --path . \
    -b main --no-checkout --fix
  ```

  from the `main` checkout. The source and validator checkouts are separate
  from the repository where PR pipelines are updated.
- Re-validates generation-specific fields from disk without `--fix`, then runs
  `conform_main_pr_children.py` and its `--check` pass. Central conformance owns
  routing, applicable scan/workspace conventions and PR platform exclusions.
  Any remaining validation error fails the job and prevents PR creation.
- Includes only `pipelineruns/**/.tekton/*.yaml` changes in the PR. Merging it
  triggers the existing PipelineRun sync workflow.
- Uploads `update-main-pr-pipelines-log` even if validation fails.

The workflow uses the existing `APP_ID` and `PRIVATE_KEY` secrets. The GitHub
App must have **Contents: read and write** and **Pull requests: read and write**
permissions on this repository. Its token allows the resulting PR to trigger
normal checks.

Concurrent runs are serialized. Each run creates a new commit and branch;
existing PR branches are never amended or force-pushed.

### Explicit directory overlays

Configure source scopes explicitly; repository names do not select overlays:

```yaml
template_overlays:
  - pipeline_dir: pipelineruns/notebooks
    template_dir: notebooks
```

`pipeline_dir` is a normalized repository-root-relative directory scope (matched
on directory boundaries); `template_dir` is relative to the configuration root
and may have an unrelated name. Source scopes must not overlap. Template roots
must exist and must not traverse symlinks. Absolute paths and traversal are
rejected. Selection precedence is component label, component prefix, directory
mapping, then base template. Without mappings only component overlays apply.
The same mapping is used for generation, validation and fix.
